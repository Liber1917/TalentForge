# 胜任力维度提炼方法论

> 本方法论改编自女娲 · Skill造人术（extraction-framework.md），
> 针对岗位胜任力建模场景调整，用于 Phase 2 框架提炼。

## 一、心智模型识别的三重验证

一个信号词要被认定为「核心胜任力维度」而非「随口一提」，必须通过三重验证：

### 验证1: 跨域复现

同一个胜任力信号出现在至少2个不同类型企业的JD中，或同时出现在JD和候选人自述中。

例：「主动闭环」——
- 出现在互联网大厂JD中
- 出现在金融科技公司JD中
- 同时出现在候选人的自述中
→ 跨类型复现 → 这是真正的核心维度

### 验证2: 有生成力

用这个维度可以推断候选人在新场景下的可能表现。

例：「认知复杂度」是核心维度——
- 面对开放问题时 → 他会先建模还是先执行？
- 面对技术争议时 → 他如何处理多约束条件？
→ 能生成新推断 → 这是真正的维度

### 验证3: 有排他性

不是所有候选人/所有岗位都这样要求，这个维度体现了该岗位的独特性。

例：「对昇腾/HBM的特定经验」不是核心维度（太具体）
「在复杂约束下保持判断力」是核心维度（有区分度）

## 二、矛盾处理原则

矛盾是胜任力模型的深度来源，不是需要修复的Bug。

### 三种矛盾类型

1. **时间性矛盾**（市场演化）
   - 早期市场强调X，新趋势强调Y
   - 处理：标注「动态维度」，说明演变轨迹

2. **行业性矛盾**（不同场景不同要求）
   - 互联网大厂要求A，传统行业要求B
   - 处理：分类型记录，不强求统一
   - 这恰好是维度适用边界的来源

3. **本质性张力**（两个维度之间的内在冲突）
   - 例：既要求「快速交付」（执行力）又要求「系统思考」（长期建设）
   - 处理：明确记录为「核心张力」
   - 这是胜任力模型中最有价值的部分

### 错误处理方式

- ❌ 选一边忽略另一边
- ❌ 编一个调和的解释
- ❌ 假装矛盾不存在
- ✅ 保留矛盾，明确张力，说明适用边界

## 三、信号归纳表的量化标准

| 信号词出现情况 | 判断 |
|-------------|------|
| ≥4类企业+候选人自述 | 强核心维度 |
| ≥3类企业出现 | 核心维度 |
| 仅2类企业出现 | 候选维度（需其他验证） |
| 仅1类企业出现 | 行业特定维度（降级） |
| 零散出现，无模式 | 丢弃 |

## 四、维度命名质量标准

| 好命名 | 坏命名 |
|-------|-------|
| 认知复杂度 | Python/Go能力 |
| 内驱与主动闭环 | 会主动问问题 |
| 韧性 | 抗压能力强 |
| 学习敏捷 | 看过很多论文 |
| 协作意识 | 参与过团队项目 |
| 方向感与标尺 | 了解业务 |

好命名的标准：
1. **可跨情境适用**（换公司换行业仍有意义）
2. **描述的是特质而非行为**（行为是证据，不是维度）
3. **有区分度**（能区分不同类型的候选人）

## 五、质量自检清单

### 维度层面
- [ ] 每个维度都在信号归纳表中有≥2类企业的来源？
- [ ] 维度数量=6？
- [ ] 每个维度都有明确的行为（二级）和证据（三级）支撑？
- [ ] 维度之间有张力但不矛盾？
- [ ] 至少2对矛盾被保留和标注？

### 行为层面
- [ ] 每个维度至少有2个行为项？
- [ ] 行为描述是可观察、可验证的？
- [ ] 行为不是技能清单？

### 证据层面
- [ ] 每个行为至少有1个证据？
- [ ] 证据不包含技能词/工具名？
- [ ] 规模词/硬件栈词降级为证据而非维度？

### 整体
- [ ] 模型能区分「好的候选人」和「普通的候选人」吗？
- [ ] 删除岗位名称后，这个模型仍然有意义吗？
- [ ] 报告输出有管理咨询报告的专业感吗？

## 六、降级词清单（快速查阅）

以下关键词**一律降为三级证据**，禁止出现在维度名称或定义中：

| 类别 | 禁止词 |
|------|--------|
| 编程语言 | Python, Go, Java, C++, Rust |
| 框架/工具 | Spring, Django, React, K8s, Docker |
| 硬件/芯片 | 昇腾, 昆仑芯, HBM, CUDA, GPU |
| 规模词 | 万卡, EB级, 10万并发 |
| 专业面 | HPC, 高性能计算, 云原生, 数据库 |
| 项目管理 | 敏捷, Scrum, 瀑布流 |
| 岗位任务 | 需求分析, 竞品分析, 用户调研 |
